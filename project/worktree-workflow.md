# Worktree Workflow — Repo-wide Rule

## Rule

**Every feature that starts gets its own Git worktree.**

- One worktree = one branch = one feature.
- Never develop a feature in the main checkout (`<repo-root>`). The main checkout stays on `main` and
  is used only to create, list, and remove worktrees.
- A branch can be checked out in only one worktree at a time; Git refuses a second checkout.
- **Worktrees are short-lived, like their branches.** The repository uses trunk-based
  development ([trunk-based-development.md](trunk-based-development.md)): a worktree is created
  from `origin/main` when its branch starts and removed right after the branch is merged
  (within 1–2 days).

---

## Location Convention

Worktrees live in a **sibling folder** of the repository, never inside it:

```
<parent>/
├── <repo-folder>/                 # main checkout (this repository)
└── repo-worktrees/
    ├── item-soft-delete/          # one folder per feature
    └── <feature-name>/
```

- Path relative to the repo root: `../repo-worktrees/<feature-name>`.
- Never create a worktree inside the repository (it would show up as untracked files).
- Never create a worktree in a temp directory (`/tmp`, `%TEMP%`, ...): it can be wiped, and
  tooling indexes (e.g. `.codegraph/`) must live under a stable path.

---

## Naming

| Kind | Branch | Worktree folder |
|---|---|---|
| Feature | `feat/<feature-name>` | `../repo-worktrees/<feature-name>` |
| Bug fix | `fix/<feature-name>` | `../repo-worktrees/<feature-name>` |
| Tooling / config | `chore/<feature-name>` | `../repo-worktrees/<feature-name>` |
| Documentation | `docs/<feature-name>` | `../repo-worktrees/<feature-name>` |

- `<feature-name>` is kebab-case (`item-soft-delete`, not `ItemSoftDelete` or `item_soft_delete`).
- The same `<feature-name>` is used for the branch, the worktree folder, and the task document
  `odd/tasks/<feature-name>.md`.
- Observed history only contains `feat/` branches (`feat/item-soft-delete`). `fix/`, `chore/`,
  and `docs/` follow the Conventional Commit types already used in commits (`feat(item)`,
  `chore(husky)`). See [git-conventions.md](git-conventions.md).

## Commands

Run every command from the **main checkout** (repo root) unless noted. Use Git Bash (or any shell
that accepts `/` paths).

### Create

```bash
git fetch origin
git worktree add --no-track -b feat/<feature-name> ../repo-worktrees/<feature-name> origin/main
```

- Base ref is `origin/main` (verified to exist), so the branch starts from the latest fetched
  `main` even if the local `main` is behind.
- `--no-track` prevents the new branch from tracking `origin/main`; its upstream is set on the
  first push (`git push -u origin feat/<feature-name>`).

### List

```bash
git worktree list
```

### Remove (after merge)

```bash
git worktree remove ../repo-worktrees/<feature-name>
git worktree prune
git branch -d feat/<feature-name>
git push origin --delete feat/<feature-name>   # only if the remote branch still exists
```

- `git worktree remove` refuses when the worktree has uncommitted or untracked changes. Commit
  or discard them first; do not add `--force` unless the work is intentionally thrown away.
- `git worktree prune` cleans up metadata of worktree folders deleted by hand.
- `git branch -d` refuses an unmerged branch. Use `-D` only when the branch is intentionally
  abandoned.

## Per-worktree Bootstrap

A new worktree contains only tracked files. Dependencies and generated files must be installed
again in each worktree, otherwise **Git hooks do not run**.

```bash
cd ../repo-worktrees/<feature-name>

# 1. Root dependencies: runs `prepare: husky`, generating .husky/_ and installing lint-staged
pnpm install

# 2. .NET service (needed by pre-push: dotnet test inventory-project/Inventory.Tests)
cd inventory-project
dotnet restore

# 3. React client (needed by pre-commit: prettier on react-client files, and by yarn scripts)
cd ../react-client
yarn install
```

Why each step is required (verified on this repository):

- `core.hooksPath` is `.husky/_`, a **relative** path stored in the shared `.git/config`, so
  every worktree uses it. Git resolves a relative `core.hooksPath` against the root of the
  working tree where the hook runs, i.e. each worktree's own `.husky/_`.
- `.husky/_/` is **not tracked**: it contains its own `.gitignore` with `*`, and only
  `.husky/pre-commit` and `.husky/pre-push` are tracked. It is generated by `husky` during
  `pnpm install`. In a fresh worktree `.husky/_` does not exist and Git silently finds no
  hooks until `pnpm install` runs.
- `pre-commit` runs `npx lint-staged`, which uses `inventory-project/.lintstagedrc.mjs`
  (`dotnet format`) and `react-client/.lintstagedrc.json` (`prettier --write`, resolved from
  `react-client/node_modules`).

> **Unverified:** the silent hook skip in a worktree without `.husky/_` follows from Git's
> documented `core.hooksPath` resolution; it has not been reproduced in a real worktree here.
> After bootstrapping, confirm hooks are active with a test commit in the new worktree.

## Shared Resources

Worktrees share the Git object database and config, but not working files. Some resources
outside Git are shared too:

| Resource | Why it is shared | Rule |
|---|---|---|
| PostgreSQL host port `5432` | The root `docker-compose.yml` publishes `"5432:5432"` | Run the database from one worktree at a time. A second `docker compose up` from another worktree fails to bind the same host port. |
| API port `5094` | Fixed in the `http` launch profile | Run the API from one worktree at a time. |
| Git config (`.git/config`) | Common to all worktrees | Do not change repo config from a worktree expecting it to stay local. |

Probably **not** shared: the Compose project, container, and `postgres_data` volume. The
compose file sets no `name:` and no `container_name:`, so Compose defaults the project name to
the folder holding `docker-compose.yml`, which is now the checkout root (`<repo-folder>` for the main
checkout, `<feature-name>` for each worktree). Each worktree therefore gets its own container
and its own named volume (`<folder>_postgres_data`), i.e. **its own database**: migrations
applied in one worktree are not visible in another, and a new worktree starts with an empty
database until `dotnet ef database update` runs there.

> **Unverified:** the per-worktree project, container, and volume names follow from Compose's
> documented default project naming and the file contents; they have not been checked with
> `docker compose ls` / `docker volume ls` in multiple worktrees. The port `5432` conflict is
> also inferred from the file, not reproduced.

Per-worktree files:

- `odd/tasks/<feature-name>.md` lives **in the feature worktree** and is committed on the feature
  branch, not in the main checkout.
- `node_modules/`, `bin/`, `obj/`, coverage output, and `.codegraph/` are per worktree. Never copy
  or symlink them from another checkout.

## Lifecycle

```
start ──► bootstrap ──► work + commit ──► push + PR ──► merge ──► clean up
```

1. **Start**: from the main checkout, `git fetch origin` and `git worktree add` (see Create).
2. **Bootstrap**: `pnpm install`, `dotnet restore`, `yarn install` in the new worktree.
3. **Work + commit**: open the editor / agent in `../repo-worktrees/<feature-name>`; create
   `odd/tasks/<feature-name>.md` for multi-step features; commit with hooks enabled; rebase on
   `origin/main` frequently.
4. **Push + PR**: `git push -u origin feat/<feature-name>`, then open a small PR to `main`
   (human decision).
5. **Merge**: done by a human on the PR, within 1–2 days of starting
   (see [trunk-based-development.md](trunk-based-development.md)).
6. **Clean up**: right after merge, from the main checkout, `git worktree remove`,
   `git worktree prune`, `git branch -d`, and delete the remote branch if still present
   (see Remove).

---

## Checklist Before Starting a Feature

- [ ] Main checkout is on `main` and clean
- [ ] `git fetch origin` done
- [ ] Worktree created under `../repo-worktrees/<feature-name>` on `feat/<feature-name>`
- [ ] `pnpm install`, `dotnet restore`, `yarn install` run inside the worktree
- [ ] No other worktree is running PostgreSQL or the API
- [ ] The change is small enough to merge into `main` within 1–2 days
